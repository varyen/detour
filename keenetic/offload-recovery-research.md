# Keenetic: offload-watchdog — research & requirements brief for an LLM agent

**Задача агента:** выяснить на ЖИВОМ Keenetic, можно ли перенести фичу
`detour-offload` (детект «залипания» аппаратного ускорения + восстановление без
ребута) — и если да, до какого уровня (полный авто-kick / только detect+notify /
невозможно). Затем реализовать то, что доказуемо работает. Это исследование +
реализация, а НЕ слепой порт.

Эта фича уже сделана и живёт на **home (GL-BE9300, QCA ipq53xx)** — используй её как
эталон:

- Скрипт-эталон: `router_files/detour-offload` (QCA-ветка: `ecm_flush` /
  `ecm_restart`, детект `qca_supported`).
- Как работает детект (**переносимо на любую платформу**): здоровый форвардинг едет
  мимо CPU в аппаратном fast-path → softirq низкий даже на 300+ Мбит; при залипании
  тот же трафик идёт софтово → **всплеск NET softirq при простое userspace-прокси**
  (проксирование грузит USER cpu, не softirq). Порог на home: `sirq% > 40 AND
  user% < 25` за 1с-дельту `/proc/stat`, стрик из 2 тиков + кулдаун 600с.
- Память проекта: `home-throughput-offload-wedge` (детали, гоча с
  `gl_front_end_*_stop`).

> ⚠️ **Ключевая гипотеза, которую надо подтвердить или опровергнуть:** на Keenetic
> восстановление, скорее всего, **невозможно из Entware** — HW NAT принадлежит
> закрытой KeeneticOS, а мы живём в userspace `/opt`. Детект — переносим. Задача:
> проверить это фактами, а не предположениями.

---

## 0. Доступ и окружение

- SSH: роутер `keenetic` в `routers.local.json`. Запуск команд: `python rsh.py
  keenetic` (stdin = скрипт) или paramiko напрямую (см. `router_config.py`). Оболочка
  — busybox `/opt/bin/sh`.
- Платформа детектится маркером `/opt/etc/ndm` или `/opt/etc/detour/platform`; пути
  `/opt/*` (см. шим в `detour-cert`/`detour-health`/`detour-offload`).
- Планировщика cron НЕТ — расписание ведёт демон `keenetic/sbin/detour-cron`
  (`S90detour-cron`). Web Push есть: `/opt/sbin/detour-push send "<t>" "<b>"`.
- HTTPS панели — KeenDNS (не наша забота для offload).

## 1. ЖЁСТКИЕ правила безопасности (это ЖИВОЙ, возможно чужой, роутер)

1. **Сначала только чтение.** Никаких записей в HW-NAT/debugfs/ndm, пока не (а)
   найден механизм и (б) подтверждён путь отката.
2. **Никаких авто-ребутов.** Reboot KeeneticOS — только с явного согласия человека,
   никогда из скрипта.
3. **Никогда не оставляй ускорение выключенным.** Любой тумблер: сохранить исходное
   значение → применить → проверить связь (`ping`) → вернуть. Есть риск повесить
   форвардинг записью в регистр frame-engine — при сомнении НЕ писать.
4. **Деструктивные тесты — только в согласованное окно** с владельцем (Keenetic-порт
   ведётся по фидбэку удалённого владельца; трафик генерирует он).
5. Кандидат, в безопасности которого ты не уверен, — **не трогай**, а вынеси в отчёт
   на ревью человеку.

## 2. ФАЗА 1 — паспорт платформы (read-only)

Собери факты, от них зависит всё остальное. Команды (интерпретация — справа по тексту):

```sh
# SoC / модель / ядро (MT7621? MT7981? — определяет движок offload)
grep -iE 'system type|machine|cpu model' /proc/cpuinfo | head; uname -a
cat /opt/etc/detour/platform 2>/dev/null
ndmc -c show version 2>/dev/null | head          # KeeneticOS версия (если ndmc есть)

# Модули ускорителя (frame engine / HW NAT). MT7621: ищи hw_nat/ra_nat/mtk_ppe/hnat
lsmod 2>/dev/null | grep -iE 'hnat|hw_?nat|ra_nat|mtk|ppe|offload|fast' 

# Доступен ли debugfs вообще (на KeeneticOS часто НЕ смонтирован/закрыт)
ls /sys/kernel/debug/ 2>/dev/null; echo "debugfs_rc=$?"
ls -d /sys/kernel/debug/*hnat* /sys/kernel/debug/*ppe* /sys/kernel/debug/mtk* 2>/dev/null

# proc-тумблеры HW NAT (классика MTK/Ralink)
ls /proc/ 2>/dev/null | grep -iE 'hwnat|hw_nat|ppe|ra_nat|hnat'
cat /proc/hw_nat 2>/dev/null | head; cat /proc/net/nf_conntrack 2>/dev/null | head -1

# softirq вообще читается? (нужно для детекта) — почти наверняка да
awk '/^cpu /{print "softirq_field="$8}' /proc/stat

# ndm как рычаг: есть ли команды про acceleration / hw-nat / fastpath
ndmc -c show 2>/dev/null | grep -iE 'accel|nat|offload|fast' 
# (аккуратно поищи в дереве ndmc — многие Keenetic имеют 'no ip nat ... hardware' и т.п.)
```

**Что установить по итогам Фазы 1:**

- **Есть ли вообще HW-offload и включён ли он.** Если Keenetic форвардит софтово по
  умолчанию (модуль не грузится / выключен) — «залипать» нечему, фича вырождается в
  «ничего делать не надо». Зафиксируй это.
- **Есть ли у нас хоть какой-то доступный рычаг** (proc/debugfs/ndmc), которым можно
  сбросить/перезапустить ускоритель БЕЗ ребута. Это главный вопрос Go/No-Go по
  восстановлению.

## 3. ФАЗА 2 — жизнеспособен ли ДЕТЕКТ (нужна нагрузка)

Детект-логика переносима, но её надо ВАЛИДИРОВАТЬ на этом железе — как на home
(A/B). Нужен реальный трафик (попроси владельца прогнать speed-test с проводного
клиента).

Метод (сэмпли раз в 1-2с во время теста):

```sh
# softirq% и user% за интервал (форвардинг-на-CPU => sirq высокий, user низкий)
awk '/^cpu /{print $8, $2+$3, $2+$3+$4+$5+$6+$7+$8}' /proc/stat   # softirq, user+nice, total
# байт-рейт по WAN/LAN интерфейсам (имена узнать: ls /sys/class/net/)
cat /sys/class/net/<wan>/statistics/rx_bytes /sys/class/net/<lan>/statistics/tx_bytes
```

Возьми за основу `router_files/detour-offload` (`cpu_sample`) и home-скрипт
`detour-abmon` (2с-сэмплер). **Проверь ключевой признак:** при здоровом offload
тяжёлый трафик идёт МИМО CPU → softirq и netdev-счётчики CPU-портов остаются низкими
даже на высокой скорости. Если так — детект применим (softirq-порог сработает при
залипании). Если у Keenetic весь форвардинг ВСЕГДА виден на CPU (нет байпаса) —
softirq-эвристика даст ложные срабатывания, нужен другой признак или детект не
годится. Зафиксируй.

**Выход Фазы 2:** «детект применим / нужен другой сигнал / не применим», с цифрами
(sirq/user под нагрузкой в здоровом состоянии).

## 4. ФАЗА 3 — жизнеспособно ли ВОССТАНОВЛЕНИЕ (самое главное, самое опасное)

Только если Фаза 1 нашла рычаг. Перебери кандидаты, каждый — по протоколу
безопасного теста (п.1). Кандидаты «kick» на MTK/Keenetic (проверять по факту):

- `ndmc` команда, отключающая/включающая аппаратное ускорение (напр. что-то вроде
  `interface ... no ip nat hardware` → назад) — если такая есть в дереве.
- proc-тумблер HW NAT (`echo 0 > /proc/hw_nat` → `echo 1`), если существует и
  писабелен из Entware (обычно НЕТ прав/ноды).
- Пересоздание nft/iptables flowtable — но на Keenetic файрвол ведёт KeeneticOS
  (`ndm/netfilter.d`), наш iptables — только поверх; вряд ли управляет offload.
- Перезапуск модуля ускорителя (`rmmod/insmod`) — **почти наверняка нельзя** (ядро
  KeeneticOS, зависимости, риск паники). Не пытаться без явного согласия.

**Протокол безопасного теста каждого кандидата:**

```text
orig=$(прочитать текущее)            # сохранить
ping -c1 <up>                        # baseline связи
применить kick                       # изменить
sleep 2; ping -c2 <up>               # связь жива?
вернуть orig / убедиться в штатном состоянии
проверить: ускорение снова активно (нагрузка → softirq снова низкий)
```

Если ни один рычаг не даёт безопасного in-place сброса → **восстановление на
Keenetic невозможно**; максимум — detect + Web Push «offload просел, перезагрузите
роутер» (ребут — вручную владельцем).

**Выход Фазы 3:** один из вердиктов —
(A) найден безопасный kick → полноценная фича;
(B) рычага нет → detect+notify (ребут вручную);
(C) offload не залипает / не наблюдается → фича не нужна.

## 5. Матрица решений → что реализовать

| Итог Фаз 1-3 | Что делать |
|---|---|
| Есть детект + безопасный kick | Полная Keenetic-ветка в `detour-offload` (по образцу QCA) |
| Есть детект, kick нет | `MODE=notify` по умолчанию: push «перезагрузите», без авто-действий |
| HW-offload нет / не залипает | Ничего; в UI пункт остаётся скрытым; задокументировать «н/д» |

## 6. Как встраивать (если Фаза 3 = A или B)

- **Скрипт:** расширить `router_files/detour-offload` — детект движка (`qca_supported`
  → добавить `keenetic/mtk_supported`), диспатч `recover()` по движку. Keenetic-шим
  для путей уже есть в файле. Детект (`cpu_sample`, пороги) переиспользуется.
- **Планировщик:** НЕ через cron (его нет). Добавить тик в `keenetic/sbin/detour-cron`
  (в его tick-расписание, рядом с health/ping). См. как там заведены другие задачи.
- **Упаковка:** добавить `detour-offload` в `keenetic/build-ipk.py` `FILES`
  (сейчас исключён; `fix_shebang=True` → `/opt/bin/sh`). Это единственный манифест
  Keenetic.
- **Конфиг:** `/opt/etc/detour/offload.conf` (`MODE=…`), seed в postinst build-ipk.py
  только если отсутствует (keeplist). На B — default `notify`, на A — `auto`.
- **UI + CGI уже готовы и Keenetic-совместимы.** `OFFLOAD_BIN="$OPT/sbin/detour-offload"`
  уже определён в Keenetic-ветке `detour-api`; actions `offload_status/set/kick`
  guard'ятся по `[ -x "$OFFLOAD_BIN" ]`. Сейчас на Keenetic файла нет → `offload_status`
  отдаёт `supported:false` → пункт меню скрыт. Как только (а) `detour-offload` попадёт
  в сборку и (б) `detect` вернёт `supported:true` — UI появится сам. Менять `detour-api`
  и `index.html` НЕ нужно.
- **Честность (release-gate):** пометить в CHANGELOG, что kick на Keenetic
  проверен/не проверен на реальном залипании; на B — прямо писать «авто-восстановление
  недоступно на этом железе, только уведомление + ручной ребут».

## 7. Формат отчёта агента (обязательно вернуть)

1. Паспорт: SoC, KeeneticOS, движок offload, включён ли, доступ к debugfs/proc/ndmc.
2. Детект: применим? цифры sirq/user под нагрузкой в здоровом состоянии.
3. Восстановление: перечень проверенных кандидатов + результат каждого (безопасно/нет/
   недоступно); финальный вердикт A/B/C.
4. Рекомендация: что реализовать (по матрице) и почему; какие правки в какие файлы.
5. Всё, что осталось непроверенным и почему (нет доступа/нет окна/риск).

## 8. Границы (чего НЕ делать)

- Не выдавать непроверенное за готовое (release-gate). Kick без живого подтверждения
  безопасности — не включать в `auto`.
- Не трогать zapret2/tpws/sing-box и файрвол KeeneticOS.
- Не подставлять реальные хосты/IP/имена в код/доки (только `*.example.com` и т.п.).
- Не коммитить/не публиковать без явного согласия.
